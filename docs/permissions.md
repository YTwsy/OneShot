# 首次使用与采集权限

OneShot 在开始新采集前需要两项独立权限：

| 权限 | 用途 |
| --- | --- |
| 屏幕录制 | 截取用户选定的应用窗口，保存为标注用的截图；不会在后台持续录屏 |
| 辅助功能 | 读取控件、文字与状态，将标注绑定到对应界面元素 |

## 首次启动

发布版首次启动显示“开始使用 OneShot”引导，并被动检查当前权限。打开引导不会自动申请系统授权或开始截图。

1. 点击“开启屏幕录制”，在系统提示中选择操作。
2. 点击“开启辅助功能”，在系统提示或设置中选择操作。
3. 从系统设置返回 OneShot 后，应用会重新检查两项状态；也可点击“重新检查”。
4. 两项都确认开启后，点击“开始使用 OneShot”。切到目标应用再按 ⌃⌥⌘S，或使用 3 秒倒计时。

每项请求单独执行。若系统提示仍在等待处理，先完成它，再请求下一项。请求按钮点击成功不代表权限已经授予；状态以新的采集进程重新检查的结果为准。

## 没有出现系统提示

曾经拒绝过请求、应用更新后的签名变化，或系统的权限状态都可能影响再次提示。引导中的每一项均提供“前往系统设置”，并显示手动路径：

- 系统设置 → 隐私与安全性 → 屏幕录制（部分版本显示为“屏幕与系统音频录制”）。
- 系统设置 → 隐私与安全性 → 辅助功能。

屏幕录制可能显示为 OneShot；辅助功能由实际读取控件的 OneShot Capture 组件请求。采集组件内置在 OneShot.app 中，权限引导会显示当前组件的名称和准确路径。只授权主应用不能代替确认采集组件的辅助功能权限。设置跳转是便利入口，不保证所有 macOS 版本都会自动定位到准确面板，因此保留手动路径。

开启后返回应用再检查。如果系统要求退出重开，先退出 OneShot，再从安装位置重新打开。当前预发布使用 ad-hoc 签名，替换应用后可能需要重新确认权限。OneShot 不自动重置权限数据库、批准权限或关闭系统安全保护。

## 辅助功能开关已开启，但引导仍显示未开启

预发布版的 ad-hoc 签名随构建变化，旧版本的授权可能不再匹配当前组件。系统列表里的开关不能代替新采集进程的实际权限检查。仅凭检查未通过，OneShot 不能自动判断是否为旧授权；下面是更新后遇到此症状时的定向恢复步骤：

1. 从安装位置打开 OneShot，在权限引导的辅助功能卡片展开“系统开关已开启，仍无法使用？”。
2. 在“系统设置 → 隐私与安全性 → 辅助功能”中，选中对应的旧授权条目（通常显示 **OneShot Capture**，也可能显示 **OneShot**），点击减号移除这一项授权记录。这不删除应用文件。组件的 Bundle 名称不一定等于系统列表名称；有多项且无法确认时，先核对，不要移除其他条目。
3. 在引导中点击“复制组件路径”，或“在 Finder 中显示”确认当前组件。
4. 在辅助功能设置点击加号，按 **⇧⌘G**，粘贴组件路径，选择该 `.app`，并开启权限。默认安装位置的路径是 `/Applications/OneShot.app/Contents/Helpers/OneShot Capture.app`；请以当前引导显示的实际路径为准。
5. 返回 OneShot，点击“重新检查”。若系统要求退出重开，先按系统提示操作。

这只涉及采集组件的辅助功能授权；不要移除 OneShot Probe 开发组件、其他应用或已有效的屏幕录制授权。修复后应先确认引导的辅助功能变为“已开启”，再采集一个包含按钮的窗口，确认上下文中包含真实 AX 节点。

Apple 的 [TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) 说明 ad-hoc 的代码要求绑定特定代码版本；[辅助功能权限指南](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac) 说明如何手动添加应用。上面的移除并重新添加是针对旧代码要求不匹配的恢复方法，仍需在当前安装版本上重新检查与验证。将来采用正式 Developer ID 签名时，需要保留一致的签名身份并验证升级行为。

## 暂时只编辑已有材料

点击“稍后设置”可以继续打开、标注和导出已有项目，不需要为离线编辑授予采集权限。再次开始新采集时会回到权限引导；也可从菜单或采集设置中的“权限与首次使用…”随时打开。

引导完成记录不会替代实际权限。后续启动或从设置返回时，如果权限已失效，应用重新显示缺失项。无法检查时显示“待确认”，不把未知状态当成已授权。

## 开发与验证

发布采集组件在标准 AppKit 启动完成后处理显式请求：

```sh
oneshot authorize --permission screen-recording --output /absolute/path/to/new-report
oneshot authorize --permission accessibility --output /absolute/path/to/another-report
```

这些是内部采集组件的 CLI 示例，不需要普通用户从终端运行。`doctor` 只检查、不请求；旧的无参数 `authorize` 仍兼容，先屏幕录制、后辅助功能。GUI 使用独立按钮，避免把两项系统交互挤在一起。

请求记录区分 AppKit 启动、实际请求类型、调用前状态、API 是否调用及 API 返回值。完成回执仅证明请求进程结束；应用会启动新的 helper 再检查授权，避免沿用旧进程中的缓存。请求返回后不再仅为等待辅助功能而保活五分钟。

`doctor.json` 与两份授权记录还包含请求进程的 Bundle ID、组件路径、PID、代码签名标识、CDHash 和 designated requirement，便于核对请求与检查是否来自同一构建。签名信息读取失败时显示 `unknown`，不影响权限检查，也不把签名有效当成权限已开启。系统实际将权限归属给哪个进程仍需结合本机 TCC 日志判断；OneShot 不读取或修改 TCC 数据库。

自动测试覆盖单项请求计划、未知／部分／全部授权状态、稍后设置、权限失效后的重新引导和检查错误后的状态清理。原生 UI 验收不自动点击系统的批准按钮；实际提示、用户批准和之后的真实采集仍须在安装后的同一应用路径验证。
