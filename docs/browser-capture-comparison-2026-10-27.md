## 直接原因：两套窗口标题并不相同

当前安装的 build 3 已在新 helper 的 `doctor` 中报告两项权限均已授予。失败诊断也成功读取 AX 窗口清单、完整标题、位置、尺寸以及 focused/main 窗口引用。这次失败不需要通过再次申请权限或修改浏览器辅助功能设置处理。

四份实际失败诊断均为 `no_matching_window`，候选清单只有一个有效窗口，CG 与 AX 的几何信息一致。差异有两种：

1. CG 标题不包含浏览器后缀，AX 标题包含准确的 ` - Microsoft Edge` 后缀。
2. 长标题在 CG 中含中间省略号 `…`，AX 中是完整标题并带浏览器后缀。

原实现同时要求标题完全相等和位置、尺寸在 3 点内相等。即使截图窗口正确，也会因标题差异在 AX 遍历前拒绝。该次截图耗时约 198 ms，AX 约 10 ms 后失败，OCR 约 1027 ms；这些是单次组件时间，不是全流程性能基准。

## 源码修正

最初的局部修正只为 Edge 兼容应用后缀与省略号。用户进一步指出其他应用也可能产生同类标题差异，因此最终实现采用通用窗口判定，移除了 Edge 特判和标题字符串归一化：

- GUI/CLI 先锁定 CG 窗口 ID 及所属 PID，再在该进程的 AX 窗口清单中判断。目标位置与尺寸必须完整、有限、有效，尺寸为正；候选的四个原始几何分量仍受 3 点容差约束。
- 完整窗口清单中只有一个几何候选、且其他候选都能排除时才接受。标题不同、为空、读取失败或被截断均不否决这一候选，也不能用于排除其他几何未知的候选。
- 多个候选的位置和尺寸都吻合时仍拒绝，即使其中只有一个标题逐字相等。某个有效几何分量明确不同时可以排除该窗口；其余几何未知且无法排除的候选继续阻止选择。
- 标题保留为观察信息，差异或不可读取写入诊断。正常采集记录的选择依据为 `unique_bounds_within_3_points`，不会宣称标题决定了窗口身份。
- 没有提供几何信息的旧 title-only API 调用仍要求有意义的标题精确匹配。正常 GUI/CLI 采集始终提供几何信息。不使用首个窗口或 focused/main 窗口替换指定目标，也不主动写浏览器的 AX 启用属性。

这项规则适用于所有应用，避免用逐应用后缀白名单修补相同机制。它仍是同一进程内基于几何的对应判断，不提供 AX 对象与 CG window ID 的直接关联，也不证明截图与 AX 正文在同一时刻原子冻结。
